# 语义查询理解与多路检索

## 1. 设计目标

系统不能依赖用户套用固定问句。对于口语、省略、倒装、跨语言和一次询问多个事实的问题，应先理解用户真正关心的业务对象、属性和条件，再检索知识库。

语义查询理解只负责“规划怎么查”，不负责回答，也不能引入知识库之外的业务事实。最终结论仍必须来自 PostgreSQL 事实表、全文索引与 pgvector 中的有效文档，并通过严格引用校验。

## 2. 结构化查询计划

除单个明确关键词外，自然语言问题会由 Qwen Plus 生成一个受限 JSON 查询计划：

```json
{
  "strategy": "semantic-qwen-v1",
  "language": "zh",
  "intent": "lookup",
  "subjects": ["翠湖授信"],
  "identifiers": [],
  "requested_facts": ["审批角色", "审批阈值", "超时时间"],
  "constraints": ["亚太北区", "高金额授权"],
  "retrieval_queries": [
    "翠湖授信 亚太北区 高金额授权 审批角色 审批阈值",
    "翠湖授信 亚太北区 高金额授权 超时时间"
  ]
}
```

例如，用户可以直接问：

```text
我这边要把那套翠湖授信放到亚太北区跑大额操作，最后谁点头、卡多少钱、等多久算超时？
```

系统不需要预先存在这条句式，也能把“谁点头”规范为审批角色，把“卡多少钱”规范为审批阈值，并保留亚太北区和高金额授权两个约束。

## 3. 检索流程

1. 原始问题执行 BM25 与向量混合检索，避免语义规划遗漏信息。
2. 查询计划中的最多4个检索子问题分别执行混合检索。
3. 使用 RRF 合并原始查询和子查询结果。
4. 用已命中的受控术语登记表发现中英文别名及下游规则、运行时、路由和发布编号。
5. 根据关联编号扩展跨文档候选。
6. 将原始问题、业务对象、请求属性和约束一起交给 Qwen Rerank。
7. 保留有效版本证据，生成回答并执行引用 ID、原文和文档状态校验。

## 4. 模型依赖控制

- 只有完整自然语言问题才调用语义规划；单个明确关键词或编号直接检索。
- 规划输出最多700 tokens、最多4个子查询，并按规范化问题缓存。
- 使用 Plus 模型池，不占用 Max 处理复杂回答的角色。
- 规划失败、超时、额度不足或 JSON 非法时，自动使用原始问题和高精度编号继续检索。
- 原问题始终参与召回，语义规划不会成为单点故障。
- `identifiers` 只能接受用户原文中真实出现的编号，模型生成的编号会被服务端丢弃。
- 查询文本按不可信数据处理，不能借由问题内容修改规划指令。

## 5. 可观测性

每次请求都会把完整查询计划保存到 `query_traces.retrieval_json.query_understanding`，包括实际策略、业务对象、编号、请求属性、约束、子查询、模型和降级原因。

## 6. 准确性保护

- 查询计划提取出的业务对象必须能在候选证据中落地；未知别名不会因为语义相似被强行映射。
- 未明确要求历史值时，默认选择 `APPROVED CURRENT` 证据；英文历史意图使用完整单词边界判断，不会把 `threshold` 误识别为 `old`。
- 模型只决定“怎么查”；编号、金额、日期和结论仍必须存在于最终引用的原文。

## 7. 评测命令

```bash
.venv/bin/python scripts/evaluate-semantic-query-understanding.py \
  --cases evaluation/semantic-query-understanding/cases.json \
  --output evaluation/semantic-query-understanding/report.json
```

## 8. 配置

```env
SEMANTIC_QUERY_UNDERSTANDING_ENABLED=true
QUERY_PLAN_CACHE_SIZE=500
QUERY_PLAN_CACHE_TTL_SECONDS=3600
```

## 9. 当前边界

- “它、上面那个、刚才的规则”等跨轮指代仍需要专门的会话指代解析。
- 内部别名关系必须由知识库证据建立，模型不能自行断言。
- 主题或属性识别成功不等于证据充分，证据不足时仍会拒答。
