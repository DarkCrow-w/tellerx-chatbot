# 业务名称＋问题：全库检索优化方案

日期：2026-09-07。方案已实施并完成本轮验收：主体识别、业务文档通道、事实排序及局部扩展已落地。标准用例两阶段合并150/150通过，新增留出题20/20通过；其中qwen3.7-flash-2026-07-15补测56/56通过，其余沿用首轮qwen3.7-flash结果，不代表单一模型全量成绩。以下保留设计及诊断依据；逐题结果与测试限制见 [升级实测报告](../evaluation/generated/stress50/upgrade-report.md)。

## 目标与范围

用户只需输入业务名称或关键词，加上要问的问题，不必知道文件名、文档类型或章节标题。例如：“青禾清算的签名算法和密钥轮换周期是什么？”系统应在该业务相关的架构、接口、运维等文档中找到事实，并保留跨文档回答能力。

本轮优先处理中文业务关键词。英文关键词在原文或已维护的名称中能直接匹配时，采用同一处理流程；暂不建设英文别名与中文业务名的自动映射、机器翻译或拼写猜测。先解决主题解析、候选误删和问题事实定位，避免把所有问题都归为跨语言检索问题。

“业务名称”是相关性线索，并不等于用户明确限定了一份文件。全库查询的授权范围仍由项目、可见性、ACL和版本状态决定，业务相关文档只是其中一个检索通道。

## 现有结果与新证据

原测试使用50份文档。排除10道英文业务名题后，150题通过143题、失败7题，且两阶段混用了Max和Flash，不能当作单模型指标。

| 类型 | 结果 | 含义 |
|---|---:|---|
| 中文业务名＋签名算法/轮换周期 | 5/10 | 同类问法对不同业务表现不稳定 |
| 中文业务名＋生产/测试并发上限 | 0/1 | 没有召回环境参数正文 |
| 明确文件＋表格参数 | 9/10 | 文件正确仍可能漏掉表格 |
| 跨文档关联 | 10/10 | 已有能力，需要保留 |
| 仅队列或负责人编号 | 15/15 | 精确内容线索有效，需要保留 |

五道中文签名查询在Max、Flash下均失败。不能仅据此断言模型无影响，但应先定位进入模型前的证据链。

本轮新增逐阶段检索追踪，发现更具体的问题：

| 案例 | 初始混合召回 | 完整实体过滤后 | 问题内容在业务文档组内检索 |
|---|---|---|---|
| q015 青禾清算签名规则 | 正确章节第1 | 正确章节被删除 | 正确章节第1 |
| q132 长风容量环境并发上限 | 正确章节第1 | 正确章节被删除 | 正确章节第1 |
| q005 澄海支付签名规则（成功对照） | 最终证据已有答案 | 当前链路仍能回答 | 正确章节第1 |
| q006 澄海支付超时与告警（跨文档对照） | 最终证据覆盖两份文档 | 当前链路仍能回答 | 运维事实第1、架构事实第2 |

对照实验中的“业务”和“问题内容”由人工从原问题拆分；文档组通过业务名检索发现，没有传入标准答案的文件ID。表中排名是候选召回排名，不是回答准确率，不能把这个实验当作已实现的自动方案。

另做了进程内过滤消融实验：临时跳过 `_prefer_complete_entity_matches` 后，q015与q132的正确正文均回到最终证据第1位；但q015同时引入了7个其他业务的同类章节，成功对照q005也引入了6个其他业务的同类章节。这个结果支持“修复主体依据与过滤策略”，不支持“简单删除所有主体约束”。

原始证据：`evaluation/generated/stress50/global-scope-probe.json`；复现：`.venv/bin/python -m evaluation.stress50.global_scope_probe`。脚本只在自己的进程内做诊断，不修改应用代码或索引，不调用回答生成。

## 首要根因：主体解析错误叠加硬过滤

`app/integrations/search.py` 的 `_query_subject_signals` 会优先采用 `_structured_subject` 的匹配结果。“是什么”等句式会将整个问题前半段当作主体：

- “青禾清算的签名算法和密钥轮换周期是什么” → “青禾清算的签名算法和密钥轮换周期”。
- “长风容量生产环境与测试环境的并发上限各是多少” → “长风容量生产环境与测试环境”。

`app/services/retrieval.py` 的 `_prefer_complete_entity_matches` 又把这一结果作为硬条件：正文、标题、文件名必须完整包含错误主体，或者包含扩展出来的某个关联编号。

与此同时，Query Plan已经识别出了“青禾清算”“长风容量”等业务名，但该过滤函数重新从原句调用旧规则，不使用已解析的主体。这导致初始召回排名第1的正确章节被删掉。剩下的内容可能只是包含ERR、RUN、RECOVERY等扩展编号的段落，所以表现为“找到了业务相关文档，但答不出具体问题”。

成功对照题同样存在主体误提取，因此不能因为某一道题答对就认定解析正确；相关编号扩展可能偶然保住答案。

## 优化顺序

### P0：统一主体解析，去掉弱判断的硬否决权

这是最先实施和验证的一步，不需要先更换Embedding或引入新的检索服务。

1. Query Plan、规则回退、实体过滤共用一个业务主体解析结果，避免三处各自解释问题。记录名称原文、在问题中的位置、解析来源、置信依据和验证结果。
2. 分离 `subjects`、`requested_facts`、`constraints`：例如业务＝青禾清算；事实＝签名算法、轮换周期；环境＝生产。不能把问句前半段整体当成业务实体。
3. 主体由文件名、已验证元数据、正文中的业务定义等来源落地验证。模型输出本身不构成强约束；没有可靠依据时保留全库召回，采用软加权。
4. 只把用户明确指定的文件ID、权限、当前版本、明确的环境条件等作为相应强约束；不能要求每个答案块都重复业务名称。有文档级关联依据即可继承到子章节。
5. 保留跨业务混淆防护：强主体锚点来自另一个业务、且没有可信关系桥接的事实不能拼接为当前业务答案。不要直接永久删除全部实体校验。
6. 调整关联编号扩展：编号须与用户所问事实或已确认业务关系有关。不要因为某段提到业务，就把其中所有RUN/RECOVERY编号都当成必须搜索的关系。

先修主体解析及过滤，再观察剩余失败。如果7道非英文失败中有些来自不同机制，应分别定位，不通过加关键词白名单硬凑结果。

### P1：增加“业务相关文档组＋问题内容”通道

在保留原问题全库通道的基础上，增加一个业务相关文档通道。仍对所有候选应用相同权限与版本过滤。

流程：

1. 拆分问题中的业务对象、所问事实、环境/区域/版本约束。
2. 发现业务相关的多份文档。第一阶段复用文件名、文档标题及正文锚点；正文发现应聚合到文档，不能只依赖文件名。现有 `document_candidates` 只适合名称候选来源，不能完整替代业务文档发现。
3. 在这个文档组内，用所问事实分别召回。例如“签名算法”和“密钥轮换周期”；保留事实词、数值单位和环境约束，而不反复靠业务名称给每个chunk加分。
4. 与原问题全库召回、精确编号召回和有依据的跨文档关系扩展合并，再统一按问题事实排序。
5. 业务候选不可靠或结果为空时，继续使用全库通道；不能因此宣布资料不存在。

初始预算可试用每业务5—10份候选文档、每事实5—10个候选章节、统一30—50个正文候选，属于待调参数。需要按相关性及文档代表性控制预算，不能让最大文档占满所有位置，也不能固定每份文档只留一块而损害跨章节答案。

用户说“澄海支付”时，同时搜它的架构、接口和运维文档是正确行为，不应要求用户选择某一份文件。只有业务对象本身无法区分，且不同对象会给出不同答案时，才需要澄清。

### P2：按照“是否回答问题”组织最终证据

文件名命中说明“与谁有关”，章节及正文匹配说明“能回答什么”。两类信号需要分别保留，避免业务名称在大量通用段落中重复出现导致拥挤。

- 章节层：用标题路径、章节摘要或首段筛选目标章节；正文层：读取该章节的实际内容、表格和必要父标题。不能只读一份文档的前N块。
- 表格：命中区域、字段或单位后带回完整目标行、表头及其环境说明，避免仅有“超时”等通用词的段落排在目标表格前。
- 多事实：为“算法＋周期”“生产＋测试”分别检查证据覆盖；只找到一项时明确回答已知项和缺失项，不能将未回答的一项自动补成默认值。
- 合并：当前 `_merge_evidence_channels` 先放完baseline再加planned。应让通道在候选层合并后统一排序或预留事实覆盖名额，避免旧通道占满证据预算。
- 扩展：当前 `document_chunks` 以文档ID、块序号排序后统一LIMIT，长文档可能耗尽预算。改为围绕命中section_id、父子节点和同表块取证，按文档/章节分配预算。
- 重复：同一模板的不同运行参考段落即使哈希不同，也可能重复表达相同内容。使用段落相似性或同事实去重，避免挤掉业务参数。

暂不把专用Rerank作为前置依赖。候选在过滤阶段已丢失时，重排无法恢复；先保证候选正确，再用固定题集对比规则排序与重排的收益、耗时和成本。

## 产品场景与决策

| 用户表达 | 处理 |
|---|---|
| “青禾清算密钥多久换一次？” | 业务文档组＋轮换事实查询，允许自然语言改写 |
| “青禾清算生产和测试的限制分别是什么？” | 保留两个环境，按环境组织事实，缺少哪项就说明哪项 |
| “Clearsea Pay的重试次数？”且名称在原文可直接匹配 | 同样拆分业务与事实；不自动推断中文别名 |
| “清算的超时是多少？”存在多个清算业务 | 查询后判断是否存在不同答案；必要时澄清具体业务，不能按最高相似度猜一个 |
| “青禾清算与澄海支付的重试策略有什么区别？” | 两个独立主体分别检索，再按相同字段比较，不把两方约束合并 |
| “DLQ-8801堆积通知谁？” | 精确编号通道，保留原有成功能力 |
| “签名失败后怎么处理？”没有业务名 | 直接全库按问题内容检索，多业务答案需要标注适用对象 |
| “某某架构文档里的超时时间？” | 沿用显式文件范围；不能用文档组通道越界补答案 |
| “青禾清算有哪些规则？” | 跨相关文档按规则类型整理；若范围过大提示细化，不默认等于文件名歧义 |
| 只有“青禾清算” | 返回业务资料概览与可追问方向，不假装用户已问了具体参数 |

## 代码落点与验证

| 位置 | 计划职责 |
|---|---|
| `app/services/query_understanding.py` | 统一业务主体、事实、约束，保留原问题中的证据位置与回退原因 |
| `app/integrations/search.py` | 修规则主体边界；提供权限内业务文档发现、事实召回和章节读取 |
| `app/services/retrieval.py` | 修硬过滤、增加业务文档通道、约束关系扩展、统一候选与覆盖检查 |
| `app/services/answering.py` | 缺项表达、条件化答案和错误分类；不依赖生成模型弥补缺失证据 |
| QueryTrace检索追踪 | 记录各阶段目标候选排名、丢弃原因、文档关联依据、事实覆盖、耗时 |

第一轮验收使用固定qwen3.7-flash及相同Embedding、相同文档版本，重新跑非英文150题，不能拼接不同模型的结果做新版本通过率。中文全库签名10题和生产/测试1题应全部通过；明确文件表格10题应全部通过；其他既有通过题不得出现范围、引用、拒答或跨业务事实混淆回归。失败必须解释到阶段，不能只报总分。

再增加独立留出题：每业务的口语改写、关键词在句中/句尾、多问题、仅名称、无名称、同名不同项目、近似名称、英文名称原文直匹配、只在正文出现的业务名，以及没有答案/有冲突的反例。调参题和留出题分开，不能只针对生成器固定句式优化。

同时报告：业务文档召回率、答案章节Recall@候选预算、最终证据前5命中、每项事实与环境覆盖率、错误业务证据率、完整回答与部分回答准确性、澄清质量和p50/p95耗时。阈值由固定基线对比确定，不将四道只读实验扩大解释为总体提升。

实施建议：先完成P0并跑固定基线；按剩余漏检类型加入P1、P2。保留开关和原路径用于对照，但回退时仍遵守显式文件范围与权限。无需先建设知识图谱、重做所有文档或更换生成模型。
