# TellerX 层级检索升级 Qwen 实测报告

评测日期：2026-09-04

评测分支基线：`codex/local-no-docker-core`

Chat 模型：`qwen3.7-max-2026-06-08`

Embedding 模型：`qwen3.7-text-embedding`（2560 维）

## 1. 结论

本次使用真实 Qwen API 验证了查询理解、上下文化 Embedding、证据约束回答和逐字引用校验。最终已覆盖的 13 个模型判断全部通过：

- 查询范围与结构识别：8/8。
- 相同正文、不同文件名的向量区分：2/2。
- 正常回答、证据不足、事实冲突：3/3。
- Qwen Chat 与 Embedding 连通性：通过。

首次运行查询理解题集时为 7/8。“项目 A 架构文档中，接口模块对重试次数有什么要求？”能够识别文档，但模型没有返回 `section_hints`。本次补充了确定性解析：当文档范围已经明确时，也会从文档范围之后的业务问题开头提取显式“模块/章节/部分”。修复后该用例真实 Qwen 复测通过，相关本地回归测试 13/13 通过。

随后使用共享 PostgreSQL 基准库完成了真实索引升级和检索复验。当前结论覆盖固定合成语料，不等价于业务专家标注的生产验收；权限隔离和既有文档完整章节树仍需单独复验。

## 3. 查询理解实测

评分要求同时检查：`retrieval_intent`、`document_hint`、显式章节提示和非空 `document_question`。

| 用例 | 预期范围 | 最终结果 |
|---|---|---:|
| 支付平台架构里的鉴权方式是什么？ | 文档：支付平台架构 | 通过 |
| 帮我看看支付平台二期这份文档，接口失败怎么处理？ | 文档：支付平台二期 | 通过 |
| 在清算系统设计中，超时后进入哪个队列？ | 文档：清算系统设计 | 通过 |
| 项目 A 架构文档中，接口模块对重试次数有什么要求？ | 文档：项目 A 架构；章节：接口模块 | 修复后通过 |
| 支付平台二期的接口模块里怎么定义签名？ | 文档：支付平台二期；章节：接口模块 | 通过 |
| 系统出现鉴权失败时应该怎么处理？ | 全库 | 通过 |
| 比较支付系统和清算系统的超时规则 | 跨来源 | 通过 |
| 鉴权失败怎么处理？ | 全库，不误判为文档 | 通过 |

首次八题共消耗 9,534 tokens，平均模型响应约 11.27 秒。修复用例单独复测消耗 1,435 tokens，约 13.91 秒。当前模型调用延迟高于产品目标中的“本地检索 P95 ≤ 3 秒”；两者口径不同，但如果 Query Plan 串行阻塞用户响应，仍需通过缓存、规则短路或更快模型降低额外时延。

## 4. 上下文化 Embedding 对照

构造两份正文和标题完全相同、仅文件名不同的接口文档：

- `支付平台二期接口说明.docx`
- `清算系统接口说明.docx`

两份正文均为“签名算法采用 HMAC-SHA256，密钥轮换周期为90天”。Embedding 输入采用“文件名 + 文档类型 + 完整标题路径 + 正文”。

| 查询 | 正确文档相似度 | 干扰文档相似度 | Top-1 |
|---|---:|---:|---:|
| 支付平台二期 接口模块 签名算法是什么？ | 0.858503 | 0.683073 | 正确 |
| 清算系统 接口模块 签名算法是什么？ | 0.828957 | 0.693626 | 正确 |

这组结果证明文件名上下文能在模板正文相同时提供显著区分信号，但样本量只有两组，不能替代 30 项目真实语料集的 Recall@K 验收。

## 6. 本次发现与处理

发现的问题不是文档范围误判，而是标题提示遗漏：原规则只识别“支付平台二期的接口模块里……”这种连写形式，没有识别“项目 A 架构文档中，接口模块……”这种先结束文档范围、再描述章节的表达。

处理方式保持有限、可解释：

- 只有已经识别出明确文档范围时才启用补充规则。
- 只读取文档问题开头显式出现、以“模块/章节/部分”结尾的标题片段。
- 不做错别字猜测、近义标题扩展或正文反推文档。
- 不改变未指定文档时的全库检索路径。

## 7. 共享 PostgreSQL 实测

共享库从 `0004_postgresql_pgvector_fts` 升级到 `0006_hierarchical_retrieval`，并用真实 Qwen 将 1,236 条搜索投影全部重建为 2560 维上下文化向量。重建耗时约 256.9 秒，最终向量指纹为 `f9a21f165550`。

### 全库 CrossDoc 基准

| 指标 | 结果 |
|---|---:|
| 问题总数 | 110 |
| 可回答问题完整来源命中 | 100/100 |
| 必需来源 Recall@10 | 100% |
| 不存在对象空证据 | 10/10 |
| 检索 P50 | 941 ms |
| 检索 P95 | 1,412 ms |

五类问题——业务操作、治理、生效、失败链路、区域比较和版本优先级——均为 20/20。

### 文档范围基准

使用 20 个业务簇的真实架构与 API 文件，构造 40 个“部分文件名 + 文档内问题”用例：

| 指标 | 结果 |
|---|---:|
| 正确解析并回答 | 40/40 |
| 目标事实命中 | 40/40 |
| 目标文档外证据 | 0 |
| 多候选正确澄清 | 1/1 |
| 不存在文档正确拒答 | 1/1 |
| 检索 P50 | 416 ms |
| 检索 P95 | 834 ms |

### 完整回答链路抽样

5 个代表问题全部通过“Qwen 查询理解 → PostgreSQL 混合检索 → Qwen 回答 → 服务端引用校验”：

- 三文档业务操作：接口、审批角色和超时均正确。
- 三文档治理：策略、保留期、变更单和生效日期均正确。
- 三文档失败链路：错误码和降级队列均正确。
- 部分文件名硬范围：只引用指定架构文档。
- 不存在业务对象：`insufficient_evidence`，没有调用回答生成模型。

端到端平均耗时约 36.4 秒，最慢约 61.3 秒。纯检索满足 3 秒目标，但串行的 Query Plan 和回答 Chat 调用使整体响应偏慢，应作为后续性能优化重点。

本轮 Rerank 保持禁用，因此上述检索结果来自 PostgreSQL BM25、Qwen Embedding、RRF、关联扩展和确定性约束。

## 8. 尚需复验

连接带 `pgvector` 且已导入验收语料的 PostgreSQL 后，还需运行：

1. 使用至少 30 个真实业务项目，而不是固定生成的 20 个业务簇，复验相似文件名 Top-1。
2. 恢复共享原始文件存储后，以 `--reparse` 为既有版本建立完整章节树并测量章节 Recall@5。
3. 使用业务专家标注问题复验全库 Recall@10、冲突和无证据拒答。
4. 使用真实 ACL 主体复验权限越界为 0。
5. 优化 Query Plan 与回答生成延迟，并分别记录模型与检索 P50/P95。

只有这些指标在真实索引上通过后，才能判定完整升级达到生产验收标准。
