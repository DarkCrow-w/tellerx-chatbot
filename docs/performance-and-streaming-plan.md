# 500 份文档场景：查询性能与流式体验优化方案

日期：2026-09-08。状态：方案，尚未实施。本方案基于当前代码及真实测试记录，不改变现有应用行为。

已确认：真实文档以 DOCX 为主，预计约500份、每份约5MB。并发人数与服务器规格尚未确定，以下延迟为待验证的规划目标。

## 1. 结论与优先顺序

建议沿两条线推进：减少实际处理时间，同时尽早展示真实工作进度。

第一优先级是模型调用策略，其次是减少串行召回和优化 SQL，再建设与引用校验兼容的流式回答。当前先保留 PostgreSQL + pgvector；是否更换检索引擎，应由真实语料压测结果决定。

500 × 5 MB 约为 2.5 GB 原始文件。文件体积不能直接换算为检索成本：图片、压缩率、扫描件、重复内容和表格都会影响解析后的文本量。查询使用提前建立的分块索引，不会每次把这 2.5 GB 文件交给模型。容量规划应看分块数、向量维度、索引体积、权限过滤选择性和并发数。

## 2. 当前证据：30 秒主要花在哪里

最近一次真实测试中，正常产生模型回答的样本：

| 阶段或指标 | Qwen 日期版本 | GLM-5.2 |
|---|---:|---:|
| 查询理解调用 P50 | 16.15 秒（130 次成功调用） | 5.77 秒（42 次） |
| 答案生成调用 P50 | 14.93 秒（116 次） | 5.63 秒（42 次） |
| 有模型回答的问题总耗时 P50 | 32.63 秒（116 题） | 13.22 秒（41 题） |
| 同类问题总耗时 P95 | 46.66 秒 | 20.30 秒 |

调用耗时取自测试开始后的 model_usage 成功记录；问题耗时取自本轮 JSONL。调用统计不是逐题配对，不应把两个 P50 相加后当作精确的单题分解。两模型承接的题目不同，不能据此宣称 GLM 在同题条件下快多少倍。不过，这些数据结合串行代码路径，足以把减少模型等待列为第一优先级。

现有测试库有 1,965 个分块，平均正文约 296 字符；chunk_search_index 连同索引约 44 MB。它并不能代表 500 份、每份 5 MB 的真实文档负载。

代码中确认的问题和已有能力：

- answering._prepare_answer 先调用查询理解，再开始检索，最后调用答案模型。
- retrieval 每轮先执行词法查询，再等待查询 Embedding 和向量查询。原问题、最多4个计划查询、最多4个事实查询，以及1个引用扩展查询按阶段串行执行。上限约10轮混合召回；已有向量缓存和查询去重，因此不等于必然发送10次 Embedding 请求。
- 编号扩展还可能逐个执行最多10个有效编号的词法查询。
- lexical_search 的候选条件包含多项 position(... in raw_text)，并对匹配行计算相似度、排序。business_documents 也从分块正文发现业务文档。数据量增长后这些路径需要重点检查执行计划。
- 数据库已有全文、exact_terms、trigram 和 HNSW 索引，HNSW 已开启 iterative_scan；不能把“加一个向量索引”当作本次的新方案。
- 查询计划和查询向量已有进程内缓存，HTTP 客户端和数据库连接池也已复用。应改进缓存键、命中率和并发行为，而非重复搭一套相同缓存。
- 前端当前使用完整 JSON 响应，等待期间只显示三个跳动圆点。
- GLM 业务概览题曾在 max_tokens=1600 时返回 finish_reason=length：1600个生成 token 全是推理 token，正文为0。仅把输出预算调大可能延长等待，不能作为唯一性能优化。

## 3. 模型侧：优先减少昂贵且不必要的调用

### 3.1 把“查询规划”和“回答生成”的模型配置分开

查询规划只做主体、文件、标题、事实和约束提取，使用低延迟、支持结构化输出的配置。普通知识查询默认不启用深度思考；复杂跨文档推理、冲突比较才按需启用。

对 GLM-5.2，可先验证网关是否支持官方的 thinking.type=disabled。官方文档确认该系列默认开启 Thinking，并提供关闭方式；当前应用使用兼容网关，仍需实际验证参数是否被支持、透传及生效。其他模型使用各自经过验证的能力配置，不把同一个参数盲目发给所有供应商。

为每个模型维护输出预算、推理开关、流式支持和结构化输出能力。记录 reasoning tokens、输出正文 tokens、finish_reason 和首段正文时间。推理预算与正文预算若不能分别控制，应通过模型能力和任务分级选配置。

### 3.2 增加保守的快速路径

| 问题类型 | 优先路径 | 升级条件 |
|---|---|---|
| UI 已选定文档 ID，且问题简单 | 直接在该文档内检索 | 问题包含比较、多项约束或意图不清 |
| 文件名＋明确标题 | 文档目录定位，再查章节正文 | 文件或标题不唯一时澄清／补规划 |
| 队列号、规则号等精确编号 | exact_terms 词法通道优先 | 证据不足、缺参数或需跨文档关联 |
| 业务名＋单一事实 | 一次基础混合召回 | 未覆盖所问事实时补充业务通道 |
| 多业务、冲突或复杂流程 | 保留完整查询规划与多轮检索 | 按原有规则处理 |

成功的快速路径有机会把两次 Chat 调用降到一次。现有“裸业务名”已经绕过模型规划，需要扩展的是其他高置信度场景。不能只凭相似度高就提前结束：还要检查文档范围、主体、问题项、环境约束和引用，避免重现此前丢失事实的问题。

### 3.3 控制生成内容与失败等待

简单事实用精简结构化回答；比较和流程题保留足够证据。重复模板段落在入库和召回时处理，围绕命中章节保留必要上下文，优先减少无关输入，而不是机械缩小所有证据预算。

给模型、检索和整次请求设置分阶段时限与统一总期限。配额耗尽立即熔断，受限流影响时有上限地退避；避免 SDK 重试、路由切换和回答纠错各自叠加，导致尾延迟失控。候选备用模型须在已配置且获准的列表中。

## 4. 检索和数据库侧：减少往返，控制规模增长

### 4.1 先去重和批量化，再做有限并发

按阶段收集不同的查询文本，一次批量请求缺失的查询向量；相同向量可在不同文档范围中复用。基础词法查询与 Embedding 可以重叠，向量返回后执行向量查询。

同一阶段互不依赖的查询以2～4路作为压测起点，设置全局并发与模型 QPS 限制。业务名修正依赖已召回文档，编号扩展依赖前一阶段的证据，这些依赖顺序要保留。合并结果仍按固定通道顺序执行，不能让网络先后顺序改变排名。

SQLAlchemy Session 不跨线程共享。并行检索各用独立连接，业务写入仍由原请求所属的 Session 管理。

### 4.2 将固定全量召回变成按需补充

第一轮优先原问题与一个高价值改写。证据充分则进入回答，否则补事实查询或编号查询。具体轮数由对照测试确定；原有完整路径作为回退保留。

这一步的收益是减少多次 Embedding 和数据库查询；风险是召回率下降。因此应独立开关、先影子对照，尤其覆盖表格、跨文档、冲突和长文档末尾，不凭速度更快就上线。

### 4.3 改造容易扩大扫描范围的 SQL

- 将全文、精确编号和模糊匹配拆成各自可利用索引的有限候选通道，再合并排序；避免复杂 OR 把过多正文拉入相似度计算。
- position() 不是 trigram 的索引检索操作。可以评估转成合适的 LIKE／ILIKE 或 trigram 操作符，但必须保持原有匹配语义，正确转义通配符；很短的中文查询可能缺少足够 trigram，需要保留专门路径。
- 先查询候选 ID 和分数，对有限候选再补齐正文与来源。避免每个召回通道重复读取整段正文和全部关联字段。
- 在入库时维护文档目录、标准业务名到文档的关系及章节索引，减少每次问答从所有分块正文推导文档组。保留正文发现作为补充；更新、删除、版本切换时同步维护。
- 对真实 SQL 执行 EXPLAIN (ANALYZE, BUFFERS)，验证全文、trigram、HNSW 是否实际参与执行，检查排序、Join、过滤及候选数量。评估向量距离后追加排序键对计划的影响，必要时内层先取有限向量候选、外层稳定排序。
- 针对权限／项目过滤评估 HNSW 的召回率和扫描深度，不能为了速度取消权限过滤或随意降低 ef_search。当前库太小，优化器选顺序扫描可能是合理选择。

### 4.4 缓存分层

优先做规范化查询向量、纯查询计划和文档目录缓存。查询计划缓存键加入模型与提示词版本，避免切换模型后继续沿用旧计划。向量缓存保留模型、维度和预处理指纹；增加并发合并，避免同一热门问题同时生成相同向量。

检索结果缓存再加入用户权限范围、项目／文档范围和索引版本。文档批准、废弃、删除或 ACL 变更必须失效。完整答案缓存放在后续阶段，只有对知识版本、权限和生成配置都能可靠校验时才使用。多进程命中率不足时再引入共享缓存，初期无需强制增加 Redis。

## 5. 前端：真实进度与经过校验的流式回答

### 5.1 用户看到什么

发送问题后立即出现一个可折叠的“处理进度”区域，步骤由后台事件驱动：

```text
✓ 已识别问题：青禾清算的签名规则
✓ 找到 3 份相关文档
✓ 已定位“安全策略”章节
● 正在整理答案并核对引用

青禾清算使用 HMAC-SHA256…… [1]
密钥每 33 天轮换一次…… [1]
```

上面的数量、标题和答案是交互示例，实际页面只能显示本次检索真实产生的数据。只展示高层工作摘要和可访问的来源，不把模型原始 reasoning_content 作为产品的“思考过程”。这样既可以让用户理解进展，也无需为了动画额外生成一段长推理。

等待期间显示已用时间；没有新进展时维持当前阶段，不制造固定百分比。提供停止按钮、断线提示、最终状态及可展开引用；用户向上阅读时暂停自动滚动，新内容到来后提示继续跟随。

### 5.2 两个阶段交付

第一阶段：状态流。

保留完整答案校验，先实时发送接收、范围定位、检索和校验阶段的事件，最终一次显示已验证答案。这能很快消除几十秒完全无反馈的体验，但不等于正文 token 流式输出，也不会单独降低模型计算时间。

第二阶段：按完整声明流式输出。

模型使用流式结构化输出。服务端增量缓冲 JSON，识别出完整声明及其原文引用后，完成范围和引用校验，再发送该段文字与引用卡片。不要按任意 token 边界直接向用户暴露不完整 JSON。新增协议可要求状态字段在前、声明逐项输出；是否支持及稳定性要对网关和模型实测。

跨文档映射先补齐来源链；冲突比较和依赖全局判断的回答，保留必要内容直到最终校验，不能把尚未确认的片段展示成确定结论。流已开始后发生后续校验失败，要有明确的失败／修正事件及最终状态；用户看到的内容与保存的最终消息保持一致。若模型无法稳定支持增量声明，保留状态流和最终答案作为回退。

### 5.3 接口与运行方式

新增 POST /api/v1/chat/stream，返回 text/event-stream；保留原 JSON 接口以兼容现有调用方。前端用 fetch 读取响应流，便于携带 POST 请求体与现有认证信息。

事件包括 accepted、stage、sources、claim、final、error，以及保活心跳。每次请求有 request_id，事件有递增序号。客户端停止／断开时关闭上游流，并尽可能停止后续任务；任务记录区分完成、中断和失败。

FastAPI 可以使用 StreamingResponse。现有阻塞模型和数据库代码需要放在受控工作线程中配合有界事件队列，或逐步改成异步适配器；只把函数声明改成 async 并不能解决阻塞。不要让长时间模型等待占住数据库事务或连接。

同时验证反向代理不缓冲事件流、空闲超时与心跳设置，以及消息分片、中文字符跨片、断流、重复事件和取消。不建议为本场景先引入 WebSocket；单向事件流已经足够，后续确有双向实时需求再评估。

## 6. 500 份文档的容量与部署

先选10～30份代表性真实 DOCX，覆盖长正文、多级标题、长表格、图片较多及格式不规范的文件，统计解析耗时、正文 token、分块数、重复率和各索引占用。其他实际存在的格式再补充采样。

DOCX 入库时保留文件名及别名、标题层级、章节路径、表格表头与行列关系，避免机械按字符切分造成标题和内容脱离。优先利用现有解析结构补齐目录索引，支持“文件→章节→分块”的定位路径；文件名或标题有歧义时保留澄清或全库检索回退。嵌入图片只有在含有需要检索的信息时才评估 OCR，并在入库阶段完成。5MB DOCX 可能有较多图片，不能直接按文件大小估算文本或向量数量。

用实测分块数推算500份规模。例如若最终是10万个1024维float32向量，仅数值约0.41GB，尚不包含HNSW、全文／trigram、正文及数据库开销；此例只是容量公式，不是对实际语料的预测。

分别测试预计规模和放大规模，并在1、5、10、20个并发问题下观察队列等待、连接池、CPU、内存、磁盘及模型限流。不能把单用户体验改善等同于多人吞吐提升。

将批量解析、Embedding和索引发布与在线问答分离，使用独立后台工作进程及各自的并发配额。当前默认在API后台执行入库，500份批量导入时更容易竞争CPU、数据库连接及模型额度。继续复用现有Outbox发布机制，先不引入新的消息系统。

服务器规格待真实分块数、并发和部署环境确认后确定。优先确保工作索引和热点数据能被有效缓存，再判断是否需要更大内存、读副本或分区；不能根据“500份文件”直接指定一种数据库集群。

## 7. 交付顺序、目标与验收

以下是规划目标，尚未实测，不承诺所有问题都能达到。

| 阶段 | 工作 | 验收重点 |
|---|---|---|
| P0 | 分阶段耗时与token埋点；统一请求ID | 能区分排队、规划、Embedding、SQL、生成首字、生成完成、校验与保存 |
| P1 | 普通查询关闭思考；查询模型独立配置；精确查找快速路径；状态流 | 首个状态目标≤0.5秒；简单题减少一次Chat调用；GLM概览不再因推理耗尽预算而空答 |
| P2 | 查询批量化、有界并发、按需扩展、SQL和目录缓存 | 在代表性500文档索引上测P50/P95、召回与权限边界；候选合并保持确定性 |
| P3 | 完整声明增量解析、校验后流式输出、取消与断线处理 | 首段已校验答案目标2～5秒（简单题）；最终正文、引用、数据库记录一致 |
| P4 | 入库隔离和并发压测、依据数据调资源 | 多用户时队列和尾延迟受控，导入任务不拖慢在线问答 |

常规事实查询的初步整体目标：在约定语料、模型和并发条件下，P50争取8～12秒、P95控制在20秒内；复杂比较单独统计。现有模型或网关若无法提供足够快的首段正文，必须调整目标或模型，不能用打字动画掩盖完成后才开始输出。

每项优化单独开关，对同一模型、同一数据版本和同一题集作前后对照。检查项包括：

- 现有170题全部重跑，单独保留当前GLM概览失败项；增加代表性真实文档问题和多人并发。
- 文件＋标题、文件＋内容、无文件名、跨文档、表格、冲突、澄清、无答案和部分答案均覆盖。
- 对原先通过的题不接受未解释的回退；若为了速度调整召回策略，须先报告并复核差异。
- 对流式回答记录首个状态、首段可用答案和最终完成时间，三者分别报告。
- 缓存命中／未命中、冷／热索引、不同权限范围分别测试；删除或权限变化后不可返回旧缓存资料。
- 超时、取消、断流、JSON不完整、供应商限流和配额耗尽有明确状态，不把失败记录算作成功。

## 8. 推荐先做的最小一批

先实施 P0 + P1：测清阶段耗时、普通查找关闭深度思考、规划模型与回答模型分开、补高置信度快速路径，以及实时状态流。它们直接对应当前观察到的主要等待，改动范围也比更换数据库小。

随后用真实语料验证 P2，再推进 P3 的校验后正文流。这样可以先交付可感知的改善，再逐步降低大库下的实际耗时，同时保留知识库回答的引用可靠性。
