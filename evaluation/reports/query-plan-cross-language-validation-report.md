# Query Plan 跨语言修复与验证报告

日期：2026-08-25  
分支：`codex/postgresql-pgvector-fts`

## 1. 问题与根因

原 Query Plan 会把“高金额授权”等业务场景误当成业务主题，并让规划后的查询结果覆盖原问题的基线结果。在中文业务名需要经术语登记表连接到英文运行时文档时，接口、拒绝码和失败队列等不透明标识证据可能被排除，最终错误拒答。

另一个风险来自多个测试知识库同时存在：未指定项目时，同名或相似实体可能从其他项目进入证据集，导致离线评测和前端问答发生项目污染。

## 2. 已实施修复

- Query Plan v2 将 named subject、scenario term、requested fact 和 constraint 分开；与事实或约束重复的伪主题会自动降级为场景词。
- 每次规划检索都保留原问题的完整基线通道，并与规划通道去重合并；错误规划不能删除基线证据。
- 从已落地证据发现的 `CTL-*`、`CORE-*`、`GATE-*` 等标识逐个执行精确词法扩展，避免多个不透明 ID 拼成一个语义查询后丢失下游文档。
- 回答 Prompt 显式传入 `REQUESTED_FACTS`，要求区分治理责任人、审批角色、操作人和升级联系人，并保留双语字段的精确值。
- Qwen 结构化调用温度固定为 `0.0`，降低 JSON 和逐字引文的随机波动。
- 引文修复只允许回到源文中的连续片段。多词英文锚点不再跨行误匹配，错误 ID 仍会被拒绝。
- 基准测试按问题所属项目强制过滤；缺少目标项目时 fail closed。
- 多项目部署时，聊天 API 未提供项目范围会返回 422；前端必须先选择项目。仅有一个项目时自动选择。

回答验收的 90% 状态、95% 引用和 98% 内容三项门槛全部通过。端到端延迟主要来自远程 Query Plan、Embedding、Rerank 与生成调用；本地检索延迟仍低于 2 秒目标。

## 6. 结论

修复后的 Query Plan 不再是检索的单点风险：原问题基线证据不可被规划删除，业务场景不会被误作强制主题，跨文档不透明标识能够确定性扩展。同时，真正不存在的业务实体会在证据主题落地阶段直接拒答，不进入生成模型猜测。

本轮测试结果满足“回答准确率高于 95%，真实无证据问题必须拒答”的要求，并达到项目内部更严格的 98% 内容准确率门槛。
